# 产品架构

> 实施状态（2026-09-08）：[Agent Harness](../harness/README.md) 已验证完成，尚未开始架构重构或产品功能实现。下一阶段由下一位 Agent 从 `ARCH-001` 开始，跨模块决策记录在 [关键记录](../关键记录/README.md)。本文的产品边界和需求内容保持不变。

## 1. 文档目的

本文档记录智能备考系统当前已经确认的产品结构、模块职责、数据关系和用户体验预期，作为后续前端架构设计、功能开发和 AI 协作的共同依据。

本文档只描述产品架构，不规定具体的前端目录、组件库、状态管理方案和后端数据库表结构。尚未确定的事项统一放在文末，后续讨论确认后再补充，不能由开发者或 AI 擅自补全为正式需求。

## 2. 产品定位

系统以“备考项目”为基本使用单位。用户先创建一个项目，再在该项目中上传资料、进行知识问答、生成模拟考试、完成作答并查看测评结果。

创建项目时只需要填写：

- 项目名称；
- 项目标签（tag）。

项目标签仅用于展示和识别，不参与问答检索、模拟考生成、评分或其他业务逻辑。

一个项目可以代表一项具体备考目标，例如一门课程考试、研究生考试、笔试或面试准备。不同项目的数据必须相互隔离。

产品希望形成以下使用闭环：

```text
创建项目
→ 上传知识资料和历年真题
→ 使用资料进行知识问答
→ 根据知识资料和历年真题生成模拟考
→ 在线作答并自动评分
→ 查看测评报告和历史记录
```

## 3. 顶层产品结构

系统顶层由项目列表和项目工作区组成。

```text
系统
├─ 项目列表
└─ 项目工作区
   ├─ 资料管理模块
   ├─ 知识问答模块
   └─ 模拟考模块
```

用户创建或选择项目后进入项目工作区。资料管理、知识问答和模拟考是项目内部的三个主要模块，所有业务数据都必须明确归属于当前项目。

## 4. 项目与数据边界

“项目”是系统最上层的业务边界。以下数据都必须归属于某个项目：

- 用户上传的知识资料和历年真题；
- 文件解析、索引和题目识别结果；
- 问答对话、消息和引用；
- 生成的模拟试卷；
- 用户的每次作答；
- 自动评分结果和测评报告。

### 4.1 项目生命周期

项目不提供归档、恢复或软删除状态。项目删除采用硬删除，并且必须级联删除项目内的全部内容：

- 知识资料和历年真题文件；
- 文件解析结果、文本分块、检索索引和题目识别结果；
- 所有问答对话、消息和引用记录；
- 生成的模拟试卷；
- 所有考试记录、用户答案、评分结果和测评报告；
- 其他仅属于该项目的运行记录和临时数据。

项目删除完成后，项目及其所有数据不再保留，不采用软删除替代，也不提供项目恢复能力。删除操作必须有明确的二次确认，避免误删。

任何模块都不能依赖一个含义不明确的“当前项目”访问数据。页面地址、接口请求和业务记录应当能够明确识别所属项目，防止不同项目的数据被错误混合。

## 5. 资料管理模块

### 5.1 模块职责

资料管理模块统一负责项目内文件的上传、查看、处理状态展示、重新处理和删除。

资料分成两个独立区域：

```text
资料管理
├─ 知识资料
└─ 历年真题
```

知识资料可以包括教材、讲义、知识点总结和其他参考资料。历年真题区域可以进一步区分真题试卷和真题参考答案，但它们仍然属于同一个历年真题区域。

### 5.2 自动处理流程

用户上传文件后，系统自动处理，不设置强制人工确认步骤。

知识资料的处理流程：

```text
上传
→ 提取文字
→ 文本分块
→ 建立检索索引
→ 可供问答和模拟考使用
```

历年真题的处理流程：

```text
上传
→ 提取文字
→ 识别题目
→ 判断题型并标注知识点
→ 关联参考答案
→ 可供模拟考使用
```

### 5.3 处理状态

资料至少需要支持以下处理状态：

- 处理中；
- 可用；
- 部分可用；
- 处理失败；
- 已移除或已删除。

真题允许部分处理成功。例如一份试卷中只有部分题目满足支持条件时，合法题目可以进入模拟考，其余题目自动排除并记录原因，不应让整份文件直接失败。

知识问答和模拟考只能读取“可用”或“部分可用”的资料，不能读取仍在处理中的半成品数据。

### 5.4 资料删除和历史记录

单独删除某份资料时：

- 新的问答和模拟考不能继续使用该资料；
- 历史问答仍保留当时的资料名称、页码和引用原文；
- 已生成的模拟试卷仍保留题目和来源快照；
- 已完成的考试记录和测评报告保持不变；
- 原文件无法继续打开时，应在历史记录中标记“原资料已移除”。

资料管理模块只决定资料以后是否可用，不能反向破坏已经形成的问答和考试历史。但如果删除的是整个项目，则按照项目硬删除规则级联删除所有历史记录，不保留任何项目数据。

## 6. 知识问答模块

### 6.1 模块职责

知识问答模块用于用户基于项目知识资料进行连续问答，并展示回答依据。

一个项目可以创建多个独立对话。每个对话分别保存自己的消息上下文、对话记录和资料引用，用户可以按章节、主题或学习任务组织对话。

### 6.2 资料范围

每个对话始终检索当前项目内全部可用的知识资料，不要求用户预先选择文件，也不提供资料范围手动限定功能。

问答模块只能使用知识资料，不能使用历年真题。

### 6.3 问答记录

系统需要持久化：

- 对话基本信息；
- 用户问题；
- 模型回答；
- 回答状态；
- 实际使用的资料名称；
- 引用页码和原文片段。

每条回答使用引用快照保存依据，避免原资料被删除后历史回答失去可读性。

## 7. 模拟考模块

### 7.1 模块定位

用户侧统一使用“模拟考”这一名称，不使用“真题预测库”等容易引起误解的名称。

大量历年真题可以用于分析题型比例、知识点频率、难度分布和历年变化，并据此进行仿真组卷，但产品不承诺准确预测真实考试题目。

### 7.2 使用的数据

模拟考同时参考两个资料来源：

- 历年真题提供题型、难度、频率、知识点分布和组卷规律；
- 知识资料提供知识内容、答案依据和题目解析来源。

只有历年真题、没有知识资料时，系统仍然可以生成模拟考。知识资料充足时，系统可以进一步增强题目内容、答案和解析的依据。

### 7.3 核心流程

模拟考不是对话式模块，其通用业务流程为：

```text
点击生成模拟试卷
→ 直接生成并保存模拟试卷
→ 在模拟试卷列表中预览
→ 点击开始答题
→ 在线作答
→ 提交答案
→ 自动评分
→ 生成测评报告
```

模拟卷生成不提供题目数量、难度、知识点范围、考试时长等配置参数。系统根据项目内可用的知识资料和历年真题直接生成模拟卷。用户可以先在模拟卷列表中预览试卷的大致信息，再决定是否开始答题。

### 7.4 试卷、作答和报告

模拟考内部必须区分三个业务对象：

```text
模拟试卷
→ 考试记录
→ 测评报告
```

一份模拟试卷可以被多次作答。每次作答都创建独立的考试记录和测评报告，不覆盖以前的答案、成绩和评价结果。

模拟试卷一旦有人开始作答，其题目、答案、评分标准和必要的来源信息应当冻结。后续资料、模型或生成规则发生变化时，不得改变已经开始或完成的考试。

作答没有时间限制，但系统记录用户本次作答花费的时间。用户可以在作答过程中保存，也可以直接退出：

- 点击保存：保存当前答案，完成评测并生成考试记录和测评报告；
- 直接退出：放弃本次作答，不保存当前答案，不进行评测，也不生成考试记录。

简答题只由 AI 进行准确度评价，不输出“正确”或“错误”的二元结论。评价结果应体现答案与参考答案、评分要点或知识资料之间的符合程度，并保留必要的评价依据。

系统需要持久化：

- 生成时的完整试卷；
- 每次考试的开始、作答和提交状态；
- 用户对每道题的答案；
- 客观题的规则评分结果；
- 简答题的 AI 准确度评价及评价依据；
- 测评报告和薄弱知识点；
- 同一试卷下的历次考试结果。

## 8. 模块依赖规则

三个模块之间的依赖方向固定如下：

```text
知识资料 ───────→ 知识问答
    │
    └──────────→ 模拟考

历年真题 ───────→ 模拟考
```

必须遵守以下约束：

- 资料管理模块负责所有资料写入、处理、停用和删除操作；
- 知识问答模块只读取知识资料；
- 模拟考模块只读取知识资料和历年真题；
- 知识问答和模拟考不能直接修改资料；
- 资料管理模块不能依赖对话、试卷或测评报告的内部实现；
- 知识问答模块与模拟考模块之间不直接共享业务状态；
- 跨模块协作通过明确、稳定的读取能力完成，不能直接访问其他模块的内部页面状态。

## 9. 用户体验预期

项目工作区应让用户清楚感知自己正在操作哪个项目，并提供三个稳定入口：

```text
资料管理｜知识问答｜模拟考
```

整体体验应满足：

- 操作路径清楚，不把大量功能堆在同一页面；
- 上传后自动处理，并明确显示处理进度和结果；
- 问答默认即可使用，不强迫用户先配置资料范围；
- 模拟考从生成、作答到报告形成连续流程；
- 模拟卷生成后可以先预览，再决定是否开始答题；
- 作答无时间限制，可以保存并评测，也可以直接退出且不保留本次作答；
- 简答题展示准确度评价，不展示简单的对错结论；
- 历史记录可重新打开，刷新页面后不丢失当前位置；
- 打开项目后默认进入知识问答页面；
- 处理中、空数据、部分成功和失败等状态都有明确反馈；
- 模块边界稳定，方便多人或 AI 在限定范围内独立开发。

## 10. 前端页面地址预期

前端应使用真实页面地址表达当前项目和业务对象，避免仅依靠临时页面状态切换模块。当前建议的地址语义如下：

```text
/projects
/projects/:projectId
/projects/:projectId/resources
/projects/:projectId/qa
/projects/:projectId/qa/:conversationId
/projects/:projectId/mock-exams
/projects/:projectId/mock-exams/:paperId
/projects/:projectId/mock-exams/:paperId/preview
/projects/:projectId/mock-exams/:paperId/attempts/:attemptId
/projects/:projectId/mock-exams/:paperId/attempts/:attemptId/report
```

具体地址名称可以在前端技术架构阶段调整，但必须保留项目、对话、试卷和考试记录的明确身份。

## 11. AI 协作预期

后续使用 AI 开发时，应遵循以下产品边界：

- 一次任务应明确属于资料管理、知识问答或模拟考中的一个模块；
- 修改公共能力时必须说明被哪些模块使用；
- 不得为了方便把项目、对话、试卷和考试记录混入一个全局状态；
- 不得在多个模块中重复实现文件上传、错误提示等通用能力；
- 不得让公共层包含某个业务模块独有的规则；
- 新需求如果改变模块职责、依赖方向或数据归属，应先更新本文档，再开始实现。

## 12. 后续待确认事项

以下内容尚未形成最终产品决策：

- 项目标签的输入与展示样式；
- 作答页面在浏览器刷新或异常关闭后的临时恢复方式；
- 简答题评分后的人工确认或申诉方式；
- 测评报告的具体指标和薄弱点计算方式；
- 资料处理失败后的重试策略和错误详情展示。

这些事项应在开发对应功能前逐项讨论，不需要在搭建前端基础架构时一次性全部决定。
