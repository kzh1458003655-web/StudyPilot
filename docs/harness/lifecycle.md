# Harness 生命周期

本流程适用于每个 Agent 会话。一次会话可以完成一个小任务，也可以只推进一个任务的一部分，但不能同时开展多个业务目标。

## 1. 初始化

1. 确认当前目录是 StudyPilot 仓库根目录。
2. 运行 `./scripts/harness-init.ps1`。
3. 阅读 [AGENTS.md](../../AGENTS.md)。
4. 阅读任务清单、当前进度和会话交接。
5. 查看当前分支、工作区状态和最近提交。
6. 阅读当前任务对应的产品、架构和关键记录文档。

初始化失败时，记录失败命令、输出摘要和影响。除非当前任务就是修复 Harness，否则不要擅自修改 Harness 来绕过失败。

## 2. 选择范围

- 只选择一个 `ready` 任务。
- 将其设为 `in_progress` 前，确认所有依赖均为 `verified`。
- 使用任务中声明的分支名；分支不存在时从包含最新 Harness 的基线创建。
- 在进度记录中写明目标、验收标准、预计修改范围和验证方式。
- 不允许提前开始 `blocked` 的产品任务。

## 3. 实施和同步

- 修改前先了解使用位置和既有测试。
- 控制改动范围，不顺手重构其他模块。
- 在开始、重要阶段完成、方案改变、发生阻塞和结束前同步进度。
- 关键设计、接口或数据库决定写入 [关键记录](../关键记录/README.md)。
- 旧代码复用写入 `重构复用清单.md`，不能只出现在 commit 信息或聊天记录中。

## 4. 验证

- 先运行与当前修改直接相关的检查，再运行任务要求的完整检查。
- 保存真实命令、结果、日期和必要的输出摘要。
- `done` 任务必须有实现结果；`verified` 任务还必须满足全部验收标准并提供证据。
- 失败验证不能通过删除测试、降低断言或修改验收标准来规避。

## 5. Commit 和 PR

- Commit 使用 `type(scope): 中文动词 + 对象`。
- 一个 commit 只表达一个完整意图，提交前通过对应检查。
- 一个任务或完整模块使用一个分支和一个 PR。
- PR 说明范围、架构影响、数据库影响、文档更新和验证证据。
- 与当前任务无关的改动留在工作区，不静默提交、不回滚。

## 6. 会话结束

1. 更新任务状态和证据。
2. 更新 `progress.md`。
3. 更新 `session-handoff.md`，给出唯一推荐下一步。
4. 同步关键记录和受影响的有效文档。
5. 运行 `./scripts/harness-check.ps1`。
6. 确认下一位 Agent 可以从标准初始化路径继续。

## 失败和阻塞

- 需求或架构不清：先查正式文档，仍不明确时请求用户决策。
- 架构文档互相冲突：记录 ADR，决策前暂停相关实现。
- 外部服务或凭据缺失：记录为外部阻塞，不写假实现冒充验证通过。
- 连续失败：保留最小复现、已尝试方案和下一步建议，停止扩大修改范围。
- 工作区包含未知改动：保留它们并调查来源，不执行 reset、checkout 覆盖或批量删除。
