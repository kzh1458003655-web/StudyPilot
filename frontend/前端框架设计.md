# StudyPilot 前端框架设计

> 实施状态（2026-09-08）：[Agent Harness](../docs/harness/README.md)、`ARCH-001` 与 `ARCH-002` 已验证完成；`ARCH-003` 已建立本文件描述的最小目标前端骨架。跨模块决定和迁移记录统一放在 [关键记录](../docs/关键记录/README.md)。

## 1. 文档目的

本文档定义 StudyPilot 前端工程的最终代码组织方式、模块边界、依赖方向和开发约束，作为后续创建前端工程、开发业务模块、代码审查以及 AI 辅助修改时的统一依据。

本文档只规定前端内部架构，不以任何现有后端、模型服务、检索服务、接口路径、字段结构、通信协议或部署方式为事实依据。所有外部系统均被视为可变化的依赖，必须通过前端边界层接入。

本文档不讨论具体产品页面、业务流程、视觉风格或模块名称。业务模块在产品设计确定后，以相同模板加入 `src/modules`。

## 3. 核心架构原则

### 3.1 模块优先

业务代码按功能模块组织。不得把全部组件、Store、接口和页面分别堆入全局技术目录。

每个模块应拥有自己的：

- 页面；
- 业务组件；
- API 声明与数据映射；
- Pinia Store；
- composable；
- 类型；
- 运行时 Schema；
- 纯工具函数；
- 路由声明；
- 测试。

### 3.2 依赖单向流动

前端依赖方向固定为：

```text
app → modules → shared
```

- `app` 可以装配业务模块和公共层；
- `modules` 可以依赖 `shared`；
- `shared` 不得依赖任何业务模块；
- 模块不得深层引用其他模块的内部文件；
- 跨模块能力必须通过模块根目录的 `index.ts` 显式公开；
- 禁止形成循环依赖。

### 3.3 外部数据与内部模型隔离

外部响应不得直接进入页面、组件或 Store。所有外部数据必须经过运行时校验和 mapper 转换，再成为前端内部模型。

### 3.4 状态就近管理

组件私有状态保留在组件中，页面流程状态优先放在页面 composable 中，只有真正跨组件或跨页面共享的状态才进入 Pinia。

### 3.5 公共能力克制增长

`shared` 只保存与具体业务无关、确实需要复用的代码。不得为了预测未来复用而提前把业务代码移动到公共层。

## 5. 顶层目录职责

### 5.1 `app`

`app` 是应用装配层，只负责：

- 创建 Vue 应用；
- 注册 Router、Pinia 和其他全局 Provider；
- 汇总模块路由；
- 提供整体布局；
- 注册全局错误兜底；
- 引入全局样式。

`app` 不实现具体业务规则，不直接定义外部接口请求。

### 5.2 `modules`

`modules` 保存所有具有明确业务语义的代码。每个模块是相对独立的功能单元，应能够明确判断其内部代码的所有权。

一个模块可以包含多个页面和组件，但不得直接访问另一个模块的内部目录。

### 5.3 `shared`

`shared` 保存业务无关的公共基础能力，包括：

- HTTP 客户端与通用错误；
- shadcn-vue 基础组件；
- 通用组合组件；
- 通用 composable；
- 配置读取；
- 设计令牌与全局样式；
- 通用类型、Schema、常量和纯函数。

禁止在 `shared` 中出现特定业务模块的字段、判断、请求路径和流程。

### 5.4 顶层 `types`

`src/types` 只保存 TypeScript 环境声明和模块扩展，例如：

- Vite 环境变量声明；
- Vue Router 的 `RouteMeta` 扩展；
- 第三方库缺失的全局声明。

普通业务类型不得放入顶层 `types`。

## 6. 业务模块内部结构

### 6.1 `api`

`api/requests.ts` 声明该模块需要的外部请求函数；`api/mappers.ts` 负责外部 DTO 与前端内部模型之间的转换。

模块 API 可以引用：

- `shared/api`；
- 本模块的 `types/api.ts`；
- 本模块的 `schemas`；
- 本模块的 mapper。

Vue 组件不得直接导入 Axios 实例，也不得直接解析外部响应。

### 6.2 `components`

保存带有本模块业务语义的组件。业务组件通过 props、emits、slots 或模块 composable 与外部交互。

组件不应：

- 直接创建 Axios 实例；
- 拼接外部请求地址；
- 依赖其他模块的内部组件；
- 承担多个无关业务流程。

### 6.3 `composables`

保存使用 Vue 响应式 API 或生命周期的可复用逻辑，文件名统一以 `use` 开头。

适合放入 composable 的内容包括：

- 页面查询和刷新流程；
- 上传、分页、筛选等交互状态；
- 可取消异步任务；
- 需要生命周期清理的监听和订阅；
- 多个组件共享但不需要全局持久化的状态流程。

### 6.4 `model`

保存 Pinia Store 和与模块状态模型直接相关的代码。Store 不负责视图渲染，也不保存仅属于单个组件的临时状态。

### 6.5 `pages`

保存被路由直接加载的页面组件。页面负责组合模块组件、调用页面 composable 或 Store，不应成为包含所有细节的巨型组件。

### 6.6 `schemas`

保存 Zod 等运行时校验对象。TypeScript 类型在编译后不存在，因此来自外部边界的数据必须由运行时 Schema 验证，不能只依赖类型断言。

### 6.7 `types`

保存本模块中被多个文件使用的独立类型。类型目录的具体规范见第 10 节。

### 6.8 `utils`

只保存本模块专用的无状态纯函数。使用 Vue 响应式 API、生命周期或持有状态的代码必须放入 `composables`。

### 6.9 `routes.ts`

声明本模块提供的路由记录，页面组件使用动态导入。模块路由由 `app/router` 汇总。

### 6.10 `index.ts`

`index.ts` 是模块唯一公共入口。只导出外部确实需要使用的页面、组件、类型或能力，禁止无差别导出模块全部文件。

## 7. 导入与依赖规则

### 7.1 路径别名

统一使用 `@/` 指向 `src/`：

```ts
import { http } from "@/shared/api/http";
```

同一小目录内可以使用相对路径；跨目录引用使用 `@/`，避免多层 `../../../`。

### 7.2 跨模块导入

禁止：

```ts
import InternalPanel from "@/modules/example/components/InternalPanel.vue";
```

允许：

```ts
import { PublicPanel } from "@/modules/example";
```

如果两个模块频繁互相引用，必须重新判断代码所有权或由 `app` 完成组合，不得用循环依赖解决。

### 7.3 类型导入

类型必须使用 `import type`：

```ts
import type { Document } from "../types";
```

TypeScript 配置启用严格模式和类型导入检查，避免类型导入被错误打包为运行时代码。

## 8. 组件分层

组件固定分为三层：

```text
shared/ui                 基础 UI 原语
shared/components         跨模块通用组合组件
modules/*/components      业务组件
```

### 8.1 `shared/ui`

保存 shadcn-vue 生成的基础组件，例如按钮、输入框、对话框和表格原语。

规则：

- 可以进行统一设计系统层面的调整；
- 不得加入业务字段、业务请求和业务判断；
- 业务页面不得复制一份相似基础组件规避公共实现；
- 修改基础组件时必须检查其全部使用位置。

### 8.2 `shared/components`

保存由多个基础 UI 组合而成、但仍不具有特定业务语义的组件，例如通用空状态、确认对话框和分页控件。

组件只有在确实跨模块复用且接口稳定时才进入该目录。

### 8.3 模块业务组件

包含明确业务含义的组件始终留在所属模块。即使其视觉结构与其他模块相似，也应先通过组合基础 UI 复用，而不是过早合并业务组件。

## 9. Pinia 状态管理规范

Pinia 使用 Composition API 风格的 Setup Store。

适合放入 Store：

- 多个页面共同读取或修改的状态；
- 路由切换后仍需保留的状态；
- 多个远距离组件共同操作的数据；
- 明确需要缓存或恢复的数据。

不放入 Store：

- 单个弹窗是否打开；
- 当前输入框文本；
- 单个按钮加载状态；
- 只在一个组件中使用的筛选项；
- Toast 文案；
- 可以由现有状态计算得到的重复数据。

Store action 可以调用本模块的 API 函数，但不得直接操作 Axios 实例。外部响应必须先经过 Schema 和 mapper，再写入 Store。

每个 Store 应提供清晰的初始化、刷新和重置能力。只有明确需要本地持久化的字段才允许写入浏览器存储，禁止默认持久化整个 Store。

Store 之间应避免相互调用；确需组合时由页面 composable 或模块级流程函数进行编排，防止循环依赖。

## 10. TypeScript 类型组织规范

### 10.1 类型就近放置

类型按所有权存放：

| 类型范围               | 存放位置                            |
| ---------------------- | ----------------------------------- |
| 仅单个组件使用         | 直接写在对应 `.vue` 文件中          |
| 模块内多个文件复用     | `modules/<feature>/types/`          |
| 多个模块通用           | `shared/types/`                     |
| 全局环境声明或模块扩展 | `src/types/*.d.ts`                  |
| 自动生成的外部契约     | 独立的 `src/generated/`，如未来需要 |

单组件使用的 `Props`、`Emits` 和局部辅助类型不单独创建文件，避免产生大量只有几行内容的碎片文件。

### 10.2 模块类型分类

```text
types/
├── api.ts
├── domain.ts
├── view.ts
└── index.ts
```

- `api.ts`：外部请求参数和响应 DTO；
- `domain.ts`：前端内部稳定使用的领域模型；
- `view.ts`：表单值、筛选条件、列表项等展示模型；
- `index.ts`：受控导出本模块允许复用的类型。

没有对应类型时无需创建空文件。

### 10.3 类型命名

统一使用有语义的后缀：

```ts
Document;
DocumentDto;
DocumentQuery;
DocumentFormValues;
DocumentListItem;
```

规则：

- 不使用 `I` 或 `T` 前缀；
- 对象结构优先使用 `interface`；
- 联合类型、映射类型和函数类型使用 `type`；
- 避免 TypeScript `enum`，优先使用 `as const` 常量和联合类型；
- 外部未知数据先使用 `unknown`，禁止直接断言为业务类型；
- 原则上禁止 `any`；确因第三方声明缺失使用时，必须局部使用并写明原因。

### 10.4 类型文件与运行时代码分离

`types` 文件只保存：

- `type`；
- `interface`；
- 类型导入与类型导出。

运行时常量放入 `constants`，Zod 对象放入 `schemas`，数据转换函数放入 `api/mappers.ts` 或对应 `utils`。

### 10.5 DTO 与领域模型

外部 DTO 和前端领域模型必须分离：

```ts
// types/api.ts
export interface ResourceDto {
  resource_id: string;
  display_name: string;
  created_at: string;
}

// types/domain.ts
export interface Resource {
  id: string;
  name: string;
  createdAt: Date;
}
```

```ts
// api/mappers.ts
import type { ResourceDto } from "../types/api";
import type { Resource } from "../types/domain";

export function mapResource(dto: ResourceDto): Resource {
  return {
    id: dto.resource_id,
    name: dto.display_name,
    createdAt: new Date(dto.created_at),
  };
}
```

页面、组件和 Store 使用 `Resource`，不使用 `ResourceDto`。

### 10.6 自动生成类型

如果未来外部服务提供 OpenAPI 或其他机器可读契约，生成类型放入：

```text
src/generated/
```

该目录满足以下规则：

- 只能由生成命令更新；
- 人和 AI 均不得手工修改；
- 业务组件不得直接依赖生成类型；
- 模块 API 层通过 mapper 将生成类型转换为内部领域类型；
- 生成命令和输入契约必须纳入版本管理。

## 11. API 与外部通信边界

### 11.1 Axios 实例

项目只创建一个普通 HTTP Axios 实例，位置固定为：

```text
shared/api/http.ts
```

该实例负责：

- 读取公开环境配置；
- 设置基础地址和合理超时；
- 添加通用请求头；
- 支持 `AbortController` 取消；
- 将网络错误转换为统一 `AppError`；
- 提供必要的请求追踪信息。

Axios 拦截器不得：

- 展示 Toast 或对话框；
- 直接操作 Pinia；
- 处理具体业务错误；
- 静默吞掉异常；
- 默认丢弃状态码、响应头等响应信息。

### 11.2 模块 API

所有具体请求只允许出现在模块 `api/requests.ts`。组件、页面和 Store 不拼接请求路径。

请求函数应：

- 接收明确类型的参数；
- 校验外部响应；
- 调用 mapper；
- 返回前端内部模型；
- 保留取消能力；
- 不产生视图副作用。

### 11.3 可替换传输方式

当前架构不预设流式协议、实时协议或外部服务实现。如未来需要 HTTP 之外的传输方式，在 `shared/api/transports` 中增加独立适配器，并由模块 API 使用。

传输适配器只处理协议，不包含业务规则。

### 11.4 统一错误

`shared/api/errors.ts` 定义统一错误模型，例如：

```ts
export interface AppError {
  kind:
    "network" | "timeout" | "cancelled" | "validation" | "business" | "unknown";
  message: string;
  code?: string;
  details?: unknown;
}
```

模块决定如何把错误转化为页面状态，视图层决定是否展示 Toast、内联提示或重试入口。

## 12. 表单与运行时校验

表单统一使用 vee-validate 管理交互状态，使用 Zod 描述校验规则。

规则：

- 前端校验负责交互体验，不代表外部系统一定接受请求；
- 表单 Schema 放入所属模块的 `schemas`；
- 页面不得散落大量手写字段判断；
- 外部响应 Schema 与表单 Schema 分开；
- 错误提示文本由表单层统一映射；
- 禁止使用类型断言绕过校验失败。

## 13. 路由规范

项目使用 Vue Router。每个模块在自身 `routes.ts` 中声明路由，由 `app/router/routes.ts` 汇总。

规则：

- 页面组件使用动态导入；
- 路由使用稳定的 `name`；
- 页面标题、布局等信息放入有类型的 `RouteMeta`；
- 路由参数进入页面后立即解析和校验；
- 路由守卫只处理导航条件，不执行复杂业务流程；
- 页面不能通过手写 URL 字符串彼此耦合。

## 14. 样式与 shadcn-vue 规范

### 14.1 设计令牌

颜色、字体、圆角、阴影和主要间距通过 CSS Variables 与 Tailwind 主题统一管理。

业务代码应优先使用语义化设计令牌，不直接散落十六进制颜色值和任意阴影。

### 14.2 全局样式

`shared/styles` 只保存：

- Tailwind 入口；
- CSS Variables；
- 字体声明；
- 基础元素样式；
- 全局主题；
- 少量跨组件动画。

业务页面的专用样式留在所属组件，不进入全局样式文件。

### 14.3 shadcn-vue

`components.json` 应至少确定：

- TypeScript 模式开启；
- UI 组件输出到 `@/shared/ui`；
- 工具函数输出到 `@/shared/utils`；
- CSS Variables 开启；
- 统一路径别名。

shadcn-vue 组件是项目源码的一部分，但对 `shared/ui` 的修改必须属于设计系统调整，不得为单个业务页面加入特例。

## 15. 异步状态规范

每个异步操作至少区分：

```text
idle
loading
success
error
```

可取消操作还应区分 `cancelled`，不得把取消显示为普通失败。

规则：

- 禁止只用一个全局 `loading` 控制全部请求；
- 禁止重复提交具有副作用的操作；
- 组件卸载时清理订阅、计时器和未完成请求；
- 较长操作应提供明确进度或阶段信息；
- 错误状态应提供恢复方式，而不是只输出控制台日志。

## 16. 工具函数与 composable 规范

### 16.1 工具函数

工具函数必须单一职责并按主题拆分：

```text
utils/date.ts
utils/file.ts
utils/number.ts
utils/text.ts
```

禁止建立不断增长的 `utils.ts`、`common.ts` 或 `helpers.ts`。

### 16.2 composable

composable 名称必须表达管理的状态或流程：

```text
useAsyncTask.ts
useFileUpload.ts
usePagination.ts
```

禁止使用 `useCommon`、`useHelper` 等无法表达职责的名称。

## 17. 命名约定

| 对象         | 约定                                      | 示例                   |
| ------------ | ----------------------------------------- | ---------------------- |
| Vue 组件     | PascalCase                                | `ResourceCard.vue`     |
| 页面组件     | PascalCase + `Page`                       | `ResourceListPage.vue` |
| composable   | camelCase，以 `use` 开头                  | `useResourceQuery.ts`  |
| Pinia Store  | camelCase，以 `use` 开头并以 `Store` 结尾 | `useResourceStore.ts`  |
| 普通函数文件 | camelCase                                 | `formatDate.ts`        |
| 类型         | PascalCase                                | `ResourceQuery`        |
| 常量         | UPPER_SNAKE_CASE                          | `MAX_FILE_SIZE`        |
| 路由名称     | 模块前缀 + 语义                           | `resource-list`        |
| 测试文件     | 与被测文件同名 + `.spec`                  | `mappers.spec.ts`      |

不得使用 `data1`、`tempData`、`handleThing`、`commonUtil` 等含义不清的名称。

## 18. 测试结构

### 18.1 单元测试

使用 Vitest 测试：

- mapper；
- Schema；
- 工具函数；
- Store action；
- composable 的状态转换。

单元测试优先与被测文件放在同一目录，便于确认所有权和同步修改。

### 18.2 组件测试

使用 Vue Test Utils 测试组件公开行为：

- props 渲染；
- emits；
- 用户点击和输入；
- 加载、空状态与错误状态；
- slots 和可访问性属性。

测试不依赖组件内部私有实现，不把快照作为唯一断言。

### 18.3 请求模拟

使用 MSW 在前端测试边界模拟外部请求。Mock 数据必须通过与真实响应相同的 Schema 校验，防止测试数据和契约长期漂移。

### 18.4 端到端测试

使用 Playwright 覆盖少量关键用户路径。端到端测试不用于穷举所有字段组合，细粒度规则由单元和组件测试覆盖。

## 19. TypeScript 与构建配置

TypeScript 配置至少满足：

- 启用 `strict`；
- 启用未使用变量和参数检查；
- 启用严格的索引访问与可空值检查；
- 使用与 Vite 一致的模块解析方式；
- 配置 `@/*` 指向 `src/*`；
- Vue 文件通过 `vue-tsc` 检查；
- 构建前必须先通过类型检查。

环境变量通过 `shared/config` 读取和解析。业务代码不得到处直接访问 `import.meta.env`。任何暴露给浏览器的环境变量都不得包含密钥。

## 20. pnpm 使用规范

前端工程统一使用 pnpm 执行依赖安装、脚本和 CLI 命令：

```text
pnpm install
pnpm add <package>
pnpm add -D <package>
pnpm remove <package>
pnpm run <script>
pnpm exec <command>
```

规则：

- 依赖安装必须在前端工程根目录执行；
- 运行脚本优先使用 `pnpm run <script>`；
- 临时调用本地工具使用 `pnpm exec`，不依赖全局安装；
- 新增或删除依赖后必须提交同步更新的 `pnpm-lock.yaml`；
- 不使用 `npm install`、`yarn` 或 `bun` 修改依赖；
- CI、开发文档和 AI 生成的命令统一使用 pnpm；
- 需要固定 pnpm 主版本时，在 `package.json` 的 `packageManager` 字段声明；
- 不把全局安装的 CLI 作为项目运行条件。

推荐在 `package.json` 中声明：

```json
{
  "packageManager": "pnpm@<locked-version>"
}
```

具体版本在创建工程时统一确定，并通过 Corepack 或团队约定保持一致。

## 21. 质量检查命令

前端工程至少提供以下脚本：

```text
dev
lint
format
format:check
typecheck
test
test:coverage
test:e2e
build
check
```

其中 `check` 应顺序执行：

```text
lint → format:check → typecheck → test → build
```

任何 AI 或成员完成代码修改后，必须执行与修改范围相称的测试；准备合并时必须通过完整 `check`。

## 22. ESLint 架构约束

ESLint 除常规 Vue 和 TypeScript 规则外，还应限制：

- `shared` 导入 `modules`；
- 模块深层导入其他模块；
- `.vue` 文件直接导入 Axios；
- 使用未说明原因的 `any`；
- 未处理的 Promise；
- 类型和值混合导入；
- 重复或无效导入；
- 未使用变量和导出。

架构约束应尽可能由工具执行，不能只依赖成员记忆或文档提醒。

## 23. AI 辅助开发约束

AI 修改前端代码时必须遵守：

1. 修改前先阅读本文档和目标模块的 `index.ts`；
2. 明确修改属于 `app`、某个模块还是 `shared`；
3. 不因方便而把业务代码移动到 `shared`；
4. 不深层引用其他模块；
5. 不在 Vue 组件中直接创建请求；
6. 不让外部 DTO 进入组件和 Store；
7. 不为单组件私有类型创建独立类型文件；
8. 不手工修改 `src/generated`；
9. 不使用 `any` 和类型断言掩盖错误；
10. 不新增第二套状态、请求、表单或 UI 方案；
11. 新增依赖前说明现有工具为什么无法满足需求；
12. 修改公共 UI 或公共类型前检查全部使用位置；
13. 修改后运行格式、Lint、类型、测试和构建检查；
14. 在交付说明中列出修改范围、公共契约变化和验证结果。

单次任务应尽量限制在一个业务模块。必须修改公共层时，应把公共层变化与模块变化分别说明，避免无关重构混入功能开发。

## 24. 新模块接入规范

新增业务模块时按以下顺序进行：

1. 在 `src/modules/<feature-name>` 创建所需目录；
2. 定义内部领域类型和必要的外部 DTO；
3. 定义外部响应 Schema；
4. 创建 mapper；
5. 创建模块 API 请求函数；
6. 根据共享范围选择页面 composable 或 Pinia Store；
7. 创建业务组件和页面；
8. 声明模块路由；
9. 通过模块 `index.ts` 暴露必要能力；
10. 在 `app/router` 中完成装配；
11. 补充 mapper、Schema、状态和组件测试；
12. 运行完整质量检查。

不得先写页面，再把页面中出现的请求、类型和状态事后随意搬到公共目录。

## 25. 架构验收标准

前端框架满足以下条件后，才能作为后续业务开发基线：

1. 使用 Vite、Vue 3 和 TypeScript；
2. 所有 Vue 组件使用 Composition API 和 `<script setup lang="ts">`；
3. 使用 Vue Router 和 Pinia；
4. shadcn-vue 以 TypeScript 模式生成到 `shared/ui`；
5. 模块、应用层和公共层依赖方向明确且可被 ESLint 检查；
6. 普通外部 HTTP 请求通过统一 Axios 实例；
7. 组件不直接依赖 Axios和外部 DTO；
8. 外部数据经过 Schema 校验和 mapper 转换；
9. 类型按组件私有、模块共享、全局共享和环境声明分别存放；
10. 单组件私有类型保留在组件内部；
11. Pinia 不保存无必要的局部 UI 状态；
12. Tailwind 与 CSS Variables 形成唯一样式基础；
13. Vitest、Vue Test Utils、MSW 和 Playwright 具有可运行入口；
14. ESLint、Prettier、vue-tsc、测试和构建可以通过统一命令执行；
15. 不包含任何既有外部系统的固定路径、字段、协议或实现假设；
16. 文档中的目录、别名和实际工程配置保持一致。

## 26. 架构变更原则

以下内容属于公共架构契约，修改前应进行集中确认：

- 顶层目录和依赖方向；
- 模块公共入口规则；
- TypeScript 类型存放规则；
- Pinia 使用边界；
- 外部 DTO、Schema、mapper 与领域模型的隔离方式；
- Axios 实例和错误模型；
- shadcn-vue 生成位置；
- Tailwind 与设计令牌方案；
- 测试工具和质量检查命令。

模块内部的页面、组件、Store、composable 和专用工具可以独立演进，只要不破坏上述公共契约。
